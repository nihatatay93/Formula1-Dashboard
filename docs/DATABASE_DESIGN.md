# Alembic and Database Model Design

Status: **accepted; Revisions 1 and 2 implemented**
Date: **2026-07-27**

This document defines the accepted database and migration design for the first historical backfill phase. Revision 1 and its six control-plane tables are implemented. Sporting-data and telemetry revisions remain planned.

## Design Goals

- Process a backfill request by year while persisting progress by event and session.
- Prevent two active backfill jobs for the same year.
- Resume safely after worker or container failure.
- Make every session ingest idempotent.
- Serve completed sessions while the rest of a year is still processing.
- Preserve the source and provisional/finalized state of imported data.
- Avoid sending full-season telemetry to clients.
- Keep the first schema compatible with plain PostgreSQL.
- Defer the TimescaleDB decision until telemetry volume is measured.

## Database Stack

- SQLAlchemy 2-style declarative models.
- Alembic for all schema changes.
- psycopg as the PostgreSQL driver.
- Synchronous SQLAlchemy sessions for the first backfill phase.
- PostgreSQL `TIMESTAMPTZ` for absolute timestamps, always interpreted as UTC.
- Integer microseconds for durations and session-relative timing values.
- `BIGINT GENERATED BY DEFAULT AS IDENTITY` for high-volume internal identifiers.
- UUID identifiers for externally visible backfill jobs.

Synchronous database access was selected because FastF1 work is blocking and the initial worker will process sessions conservatively. This avoids maintaining separate synchronous and asynchronous model layers. The live timing phase can reassess the database access pattern without changing the relational schema.

## Alembic Conventions

### Connection configuration

- `alembic/env.py` reads `DATABASE_URL`.
- SQLAlchemy URLs use the explicit psycopg dialect: `postgresql+psycopg://`.
- Secret values remain in environment variables and are never written to Alembic files.
- Offline SQL generation remains supported.

### Naming convention

SQLAlchemy metadata will use deterministic names:

```python
{
    "ix": "ix_%(table_name)s_%(column_0_N_name)s",
    "uq": "uq_%(table_name)s_%(column_0_N_name)s",
    "ck": "ck_%(table_name)s_%(constraint_name)s",
    "fk": "fk_%(table_name)s_%(column_0_N_name)s_%(referred_table_name)s",
    "pk": "pk_%(table_name)s",
}
```

Every check constraint must have an explicit short name so generated names remain deterministic.

### Autogeneration policy

- Autogeneration is a starting point, not an approval mechanism.
- Every generated revision must be reviewed before it is committed.
- `compare_type=True` and `compare_server_default=True` will be enabled.
- A revision must contain both `upgrade()` and a reviewed `downgrade()`.
- Data-destructive downgrades must state that risk in the revision docstring.
- Schema changes must not be generated or run automatically during API startup.

### Local migration execution

A one-shot `migrate` Compose service is built from the backend image. The API and worker start only after that service completes successfully. This prevents concurrent API and worker processes from racing to apply migrations.

Verified commands:

```bash
docker compose run --rm migrate /opt/venv/bin/alembic upgrade head
docker compose run --rm migrate /opt/venv/bin/alembic current
docker compose run --rm migrate /opt/venv/bin/alembic check
docker compose run --rm migrate /opt/venv/bin/alembic downgrade base
```

Revision generation remains documented but has not yet been verified:

```bash
docker compose run --rm migrate /opt/venv/bin/alembic revision --autogenerate -m "description"
```

## Migration Phases

### Revision 1: Backfill control plane

Creates:

- `seasons`
- `events`
- `sessions`
- `session_ingestions`
- `backfill_jobs`
- `backfill_job_sessions`

This revision is enough to discover a schedule, create one year-level job, track every session, recover work, and expose progress. It deliberately does not store laps or telemetry.

### Revision 2: Sporting data

Creates:

- `drivers`
- `session_entries`
- `session_results`
- `laps`

This revision enables one complete FastF1 session backfill without committing to a telemetry storage strategy.

### Revision 3: Telemetry

Deferred until FastF1 storage volume and query patterns are measured. The decision will cover:

- Plain PostgreSQL versus TimescaleDB.
- One unified sample table versus separate car-data and position-data tables.
- Time partitioning and retention.
- Compression.
- The uniqueness key used after FastF1 car and position streams are merged.

## Implemented Control-Plane Tables

### `seasons`

Represents one Formula 1 season and its schedule freshness.

| Column | Type | Notes |
| --- | --- | --- |
| `year` | `SMALLINT` | Primary key; check `year >= 1950`. |
| `coverage_checked_at` | `TIMESTAMPTZ` | Last successful upstream schedule/coverage check. |
| `coverage_valid_until` | `TIMESTAMPTZ` | Null for unknown coverage; used to derive `stale`. |
| `created_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `updated_at` | `TIMESTAMPTZ` | Updated by application writes. |

The season status is derived rather than stored. This avoids a mutable season status drifting away from session and job state.

### `events`

Represents one championship event in a season.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGINT IDENTITY` | Primary key. |
| `season_year` | `SMALLINT` | Foreign key to `seasons.year`, delete restricted. |
| `round_number` | `SMALLINT` | Championship round number. |
| `official_name` | `TEXT` | Nullable upstream official name. |
| `event_name` | `TEXT` | Display name. |
| `country` | `TEXT` | Nullable normalized display value. |
| `location` | `TEXT` | Nullable circuit/location display value. |
| `event_format` | `TEXT` | Nullable FastF1 event format. |
| `starts_at` | `TIMESTAMPTZ` | Nullable event start. |
| `ends_at` | `TIMESTAMPTZ` | Nullable event end. |
| `source` | `TEXT` | Source check constraint. |
| `created_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `updated_at` | `TIMESTAMPTZ` | Updated by application writes. |

Constraints and indexes:

- Unique `(season_year, round_number)`.
- Index `(season_year, starts_at)`.

The first backfill slice is limited to championship rounds. Supporting testing events with round number `0` would require a later explicit scope change.

### `sessions`

Represents one session within an event.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `BIGINT IDENTITY` | Primary key. |
| `event_id` | `BIGINT` | Foreign key to `events.id`, delete restricted. |
| `session_key` | `TEXT` | Internal canonical key such as `race` or `qualifying`. |
| `session_name` | `TEXT` | Upstream/display name. |
| `scheduled_start_at` | `TIMESTAMPTZ` | Nullable planned start. |
| `scheduled_end_at` | `TIMESTAMPTZ` | Nullable planned end. |
| `source` | `TEXT` | Source check constraint. |
| `created_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `updated_at` | `TIMESTAMPTZ` | Updated by application writes. |

Constraints and indexes:

- Unique `(event_id, session_key)`.
- Index `(event_id, scheduled_start_at)`.

`session_key` is text rather than a PostgreSQL enum because Formula 1 session formats can evolve. Canonical values will be validated by the application and normalized at the ingestion boundary.

### `session_ingestions`

Stores the persistent latest ingestion state for a session, independently from any one job.

| Column | Type | Notes |
| --- | --- | --- |
| `session_id` | `BIGINT` | Primary key and foreign key to `sessions.id`. |
| `status` | `TEXT` | `pending`, `running`, `completed`, or `failed`. |
| `source` | `TEXT` | `live_signalr`, `fastf1_archive`, or `jolpica`. |
| `record_state` | `TEXT` | `provisional` or `finalized`. |
| `attempt_count` | `INTEGER` | Non-negative, default `0`. |
| `first_started_at` | `TIMESTAMPTZ` | Nullable. |
| `last_started_at` | `TIMESTAMPTZ` | Nullable. |
| `heartbeat_at` | `TIMESTAMPTZ` | Nullable worker heartbeat/lease evidence. |
| `next_retry_at` | `TIMESTAMPTZ` | Nullable retry eligibility time. |
| `completed_at` | `TIMESTAMPTZ` | Nullable. |
| `source_updated_at` | `TIMESTAMPTZ` | Nullable upstream data timestamp when available. |
| `last_error_code` | `TEXT` | Nullable safe diagnostic code. |
| `last_error_message` | `TEXT` | Nullable sanitized diagnostic summary. |
| `created_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `updated_at` | `TIMESTAMPTZ` | Updated by application writes. |

Constraints and indexes:

- Named checks for `status`, `source`, `record_state`, and non-negative `attempt_count`.
- Index `(status, next_retry_at)`.
- Index `(heartbeat_at)` for recovery scans of running sessions.

### `backfill_jobs`

Stores one year-level backfill request.

| Column | Type | Notes |
| --- | --- | --- |
| `id` | `UUID` | Primary key, generated by the application. |
| `season_year` | `SMALLINT` | Foreign key to `seasons.year`, delete restricted. |
| `status` | `TEXT` | `pending`, `running`, `completed`, or `failed`. |
| `request_reason` | `TEXT` | `missing`, `partial`, `stale`, or `manual`. |
| `requested_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `started_at` | `TIMESTAMPTZ` | Nullable. |
| `heartbeat_at` | `TIMESTAMPTZ` | Nullable. |
| `completed_at` | `TIMESTAMPTZ` | Nullable. |
| `last_error_code` | `TEXT` | Nullable safe diagnostic code. |
| `last_error_message` | `TEXT` | Nullable sanitized diagnostic summary. |

Constraints and indexes:

- Named checks for `status` and `request_reason`.
- Partial unique index on `season_year` where status is `pending` or `running`.
- Index `(status, requested_at)`.

The partial unique index is the database-level guarantee that two active jobs cannot exist for the same year. The API should catch the unique violation and return the existing active job.

### `backfill_job_sessions`

Stores per-session progress and attempt history within a year-level job.

| Column | Type | Notes |
| --- | --- | --- |
| `job_id` | `UUID` | Foreign key to `backfill_jobs.id`, delete cascades. |
| `session_id` | `BIGINT` | Foreign key to `sessions.id`, delete restricted. |
| `status` | `TEXT` | `pending`, `running`, `completed`, or `failed`. |
| `attempt_count` | `INTEGER` | Non-negative, default `0`. |
| `queued_at` | `TIMESTAMPTZ` | Server default `now()`. |
| `started_at` | `TIMESTAMPTZ` | Nullable. |
| `heartbeat_at` | `TIMESTAMPTZ` | Nullable. |
| `next_retry_at` | `TIMESTAMPTZ` | Nullable. |
| `completed_at` | `TIMESTAMPTZ` | Nullable. |
| `last_error_code` | `TEXT` | Nullable safe diagnostic code. |
| `last_error_message` | `TEXT` | Nullable sanitized diagnostic summary. |

Constraints and indexes:

- Composite primary key `(job_id, session_id)`.
- Named checks for `status` and non-negative `attempt_count`.
- Worker claim index `(status, next_retry_at, queued_at)`.
- Job progress index `(job_id, status)`.

## Accepted Sporting-Data Design

Revision 2 is fully specified in `docs/SPORTING_DATA_DESIGN.md` and implemented by Alembic revision `20260728_0002`.

Key decisions:

- Historical ingestion begins with 2018.
- Global driver identity uses internal IDs and verified external identifiers.
- Racing number belongs to a session entry and is unique only within one supported session.
- Unresolved session entries may have a null `driver_id` and use a deterministic `entry_key`.
- Results use explicit normalized elapsed-time and leader-gap fields.
- Laps include timing, pit, tyre, speed-trap, position, deletion, and data-quality summaries, but no raw telemetry.
- Future ingestion will load race-control messages for deleted-lap accuracy while keeping telemetry and weather disabled for sporting-data backfill.

## Status Derivation

### Session status

The persisted `session_ingestions.status` is authoritative for session ingestion progress.

### Year status

Year status is derived from coverage, the active job, and session states:

1. `missing`: no discovered sessions or no ingestion records.
2. `pending`: an active job exists but no session is running or completed.
3. `running`: at least one session is running.
4. `partial`: at least one session is completed while another required session is pending, running, or failed.
5. `completed`: every required discovered session is completed and coverage is fresh.
6. `stale`: every required discovered session is completed but season coverage has expired.
7. `failed`: no useful completed coverage exists and the job/session work is terminally failed.

The exact precedence will be implemented once API response tests are written.

## Idempotency and Concurrency

- Season creation uses an upsert keyed by `year`.
- Event creation uses an upsert keyed by `(season_year, round_number)`.
- Session creation uses an upsert keyed by `(event_id, session_key)`.
- Session entries use an upsert keyed by `(session_id, entry_key)`.
- Laps use an upsert keyed by `(session_entry_id, lap_number)`.
- A partial unique index prevents two active year jobs.
- Workers claim eligible `backfill_job_sessions` rows with `FOR UPDATE SKIP LOCKED`.
- One database transaction changes a claimed job-session and its persistent session-ingestion state to `running`.
- A completed session is committed independently, so later sessions failing does not hide completed data.
- Re-running a completed session updates/upserts its owned rows instead of blindly inserting duplicates.
- Destructive replacement of a session dataset, if required, must happen inside one transaction after the replacement data has been validated.

## Retry and Crash Recovery

Accepted target behavior:

- Retry is scoped to a session, never to the entire season from the beginning.
- `attempt_count` increments when a worker successfully claims a session.
- Retryable failures set `next_retry_at`; permanent validation failures remain failed.
- Maximum attempts and backoff are configuration values, not schema constants.
- Running rows with an expired heartbeat become eligible for recovery.
- Recovery must not reset a completed session.
- Error fields contain sanitized summaries only and must never contain credentials, cookies, or raw authorization headers.
- The initial worker processes one FastF1 session at a time.

Exact lease duration, heartbeat interval, retry count, and backoff schedule remain open decisions.

## Data Source and Finalization

Source and record-state values use text columns with named check constraints instead of native PostgreSQL enums.

Reasons:

- New sources or states can be introduced with a normal constraint migration.
- Alembic upgrade and downgrade logic stays simpler.
- Application code can still expose typed Python enums.

Initial source values:

- `live_signalr`
- `fastf1_archive`
- `jolpica`

Initial record states:

- `provisional`
- `finalized`

Historical FastF1 archive imports are normally finalized. Live SignalR rows remain provisional until reconciliation completes.

## Deletion and Retention

- Season, event, session, and sporting-data foreign keys default to restricted deletion.
- Job-session rows cascade only when their parent job is explicitly deleted.
- Backfill should repair data through idempotent upserts, not broad deletes.
- Telemetry retention will not be decided before volume measurements.
- No automatic cleanup job is part of the first migration.

## Accepted Implementation Decisions

1. SQLAlchemy 2 synchronous sessions for the first backfill phase.
2. A one-shot `migrate` Compose service.
3. Derived rather than persisted year status.
4. Championship rounds only for the first slice, excluding testing events.
5. Text plus named check constraints instead of PostgreSQL enums.
6. Phased migrations: control plane, sporting data, then telemetry.

## Remaining Open Decisions

1. Define current-season coverage freshness.
2. Define retry count, backoff, heartbeat, and lease defaults.
3. Decide whether manual job cancellation is required in the first phase.

## Acceptance Criteria for the First Migration

All criteria below were verified on 2026-07-27 against an isolated PostgreSQL 17 Compose instance:

- Upgrade succeeds against an empty PostgreSQL database.
- Downgrade returns the database to the pre-migration state.
- A second upgrade is a no-op.
- Two active jobs for the same year cannot be inserted.
- Multiple completed or failed historical jobs for the same year can exist.
- Duplicate event and session natural keys are rejected.
- Invalid status, source, and record-state values are rejected.
- A worker-claim query can use the intended pending/retry index.
- Alembic reports the database at `head`.
- Integration tests run inside Docker without depending on a host virtual environment.
